# Decisions

Each entry: the decision, the alternatives, the reason.

## D1 — Licence: MIT
- Alternatives: Apache-2.0, MPL-2.0.
- Reason: The build plan's default; the most permissive option for a Marketplace extension.

## D2 — Repository visibility: private until first release
- Alternatives: public from day one.
- Reason: Visibility wasn't specified. Private is the reversible choice; switch with `gh repo edit --visibility public`.

## D3 — Extra crate `indexer/crates/engine` for the indexing pipeline
- Alternatives: put the pipeline in `crates/rpc` (the binary) or in `crates/parse`.
- Reason: The pipeline (discover → hash → parse → resolve → analyse → persist, plus incremental updates) depends on core, parse and git. A separate library crate keeps it testable without the RPC layer, and lets property tests compare incremental and cold runs directly.

## D4 — Protocol bindings generated by a small Node script (`protocol/gen.mjs`)
- Alternatives: JSON Schema with quicktype/typify; hand-written types on both sides.
- Reason: The protocol is small. A ~150-line generator with no dependencies emits serde structs and TS interfaces from one `schema.json`. CI runs `gen --check` so the two sides can't drift.

## D5 — LSP-style `Content-Length` framing for JSON-RPC over stdio
- Alternatives: newline-delimited JSON.
- Reason: Same framing as language servers, robust to newlines in payloads and to partial reads; base64 tile buffers can be large.

## D6 — CI: native test on 3 platforms, cross-compile the other 3
- Alternatives: native ARM runners (`ubuntu-24.04-arm`, `windows-11-arm`) and Intel macOS runners.
- Reason: ARM and Intel-mac hosted runners aren't reliably available to private repos. linux-arm64, win32-arm64 and darwin-x64 are built (and packaged as VSIX) by cross-compiling; tests and VS Code integration tests run natively on linux-x64, win32-x64 and darwin-arm64. Revisit when the repo goes public.

## D7 — Bench startup scenario does one warm-up spawn
- Alternatives: report the first spawn.
- Reason: The first launch of a freshly built binary measured 1236 ms on Windows, dominated by the OS scanning a new executable; steady-state launches measured 18–20 ms. Users pay the scan once per install, not per activation.

## D8 — Treemap layout computed in the indexer, not the webview
- Alternatives: send the node list to the webview and lay it out there (the plan lists `webview/src/layout/` for the treemap).
- Reason: The plan also says the webview gets only what is visible, streamed as tiles from the indexer. Tiles can only be cut where the geometry is known, so the squarified layout lives in `indexer/crates/core/src/layout.rs`. `webview/src/layout/` keeps the client-side layout work: hit-testing (quadtree), and later edge bundling and ELK.

## D9 — Glyph atlas rasterised at the exact label size instead of an SDF atlas
- Alternatives: signed distance field atlas, as the plan suggests.
- Reason: Labels are drawn only at 11, 12 and 13 px and never scale with zoom, so SDF's benefit (one atlas for any size) doesn't apply. At these sizes SDF glyphs come out softer than glyphs rasterised at size × devicePixelRatio. Glyphs are added on demand, so any Unicode label renders.

## D10 — Generated and vendored files stay on the map but are never parsed; node_modules and VCS dirs are excluded
- Alternatives: drop generated files entirely.
- Reason: Generated code is part of the repository and takes space people should see (kubernetes vendors a third of its files). Showing it, flagged and drawn in a quieter fill, is more honest than hiding it. Parsing it would waste indexing time, so it isn't parsed. `node_modules`, `.git`, `.hg` and `.svn` are never part of the project's own code.

## D11 — Warm start skips re-hashing files whose size and mtime are unchanged
- Alternatives: hash every file on every start (BLAKE3 is fast).
- Reason: Reading 60k+ files costs seconds on a cold disk cache even when nothing changed. Size+mtime is the same shortcut git uses. The content hash stays the cache key, so branch switches reuse parse results whenever content matches.

## D12 — Tile item coordinates are tile-relative f32, and stay tile-relative on the GPU
- Alternatives: absolute world f32 coordinates; one global batch rebased to the viewport.
- Reason: At the deepest zoom a symbol is about 1e-7 world units wide, below f32 resolution near 1.0. Tile-relative coordinates decode exactly into f64 world positions. Since D15 each tile's GPU batch keeps them tile-relative too, so f32 stays precise at any zoom without rebasing. (Superseded: the first version rebuilt one global batch rebased to the viewport.)

## D15 — One GPU batch per tile, scissored to the tile; selection drawn as an overlay
- Alternatives: one global scene of up to 50k deduplicated items, rebuilt when any tile arrives (the first M1 version).
- Reason: Profiling linux at file level showed the global rebuild (dedup, sort, quadtree, upload of 50k items) costing up to 290 ms per arriving tile: 44.6 fps with 19 frames over 32 ms. Per-tile batches are built once (and only within a per-frame budget), panning changes only uniforms, and the scissor keeps painter's order correct without cross-tile sorting. Hover, pins, selection and "you are here" are a small overlay, so they never rebuild tiles. Result: 58–60 fps, draw CPU p90 about 5–7 ms.

## D16 — Warm start reads a single file-list snapshot and gives the first view priority
- Alternatives: read 86k rows from SQLite; start reconciliation right away.
- Reason: Profiling the linux warm start: row loading (58–290 ms) plus graph insertion (240–420 ms) put the map at 491–740 ms against a 500 ms budget. A postcard snapshot written when indexing goes idle loads in about 40–55 ms, the layout is computed before the map is announced, and search indexing and discovery wait (at most 300 ms) for the first tiles to be served. Result: 222–383 ms. Rows stay authoritative; a stale snapshot only makes discovery re-check more files.

## D17 — On Windows, cold-index time is bound by antivirus file scanning; measure it, don't hide it
- Alternatives: report only warm-cache numbers; add Defender exclusions in the bench.
- Reason: With Windows Defender real-time protection on, a plain Python reader needs 217 s (399 files/s) to read linux once. The indexer's 98–308 s cold runs track that baseline, and its compute (parse-free M1 layer) is milliseconds. Adding exclusions would change the user's security settings. Compass mitigates instead: the map is usable from discovery (about 0.6 s, sizes estimated), warm starts never re-read unchanged files (D11), and CI measures cold budgets on Linux runners (`bench-nightly.yml`).

## D18 — M1 gate evaluated on this laptop, below the reference machine
- Alternatives: block M2 until a reference machine (8 cores, 16 GB) is available.
- Reason: Only an i5-1135G7 (4C/8T, 8 GB, Iris Xe) is available. All M1 budgets are met here except the strict "no frame over 32 ms": 58–60 fps, most runs show 0–3 single missed vsyncs in 300 frames while tiles stream in. The remaining per-frame CPU is under 8 ms at p90, so the misses come from the machine's variance (identical runs differ 2×), not from a structural cost. Proceeding to M2; the frame budget is re-checked with `webview/harness/perf.mjs` on each milestone and recorded in PROGRESS.md.

## D13 — Lines of code = non-blank lines
- Alternatives: physical lines; or code lines excluding comments.
- Reason: Non-blank lines are cheap to count during hashing and language-independent. Excluding comments would need a parse per language and make area depend on tier.

## D14 — A standalone webview harness for visual and performance tests
- Alternatives: screenshot the webview inside VS Code via test-electron.
- Reason: Playwright can't reach into a VS Code webview iframe reliably. `webview/harness/` serves the same bundle with a stand-in for `acquireVsCodeApi`, theme tokens copied from VS Code's built-in themes, and a real indexer behind it. The integration test still covers the real VS Code path.

## D19 — mimalloc as the indexer's allocator, including tree-sitter's C allocations
- Alternatives: the system allocator.
- Reason: Parsing allocates heavily from 8 threads; profiling showed a file taking 4.2× longer in the parallel run than alone. mimalloc (routed into tree-sitter via `ts_set_allocator`) took vscode's cold index from 13.7 s to 12.9–13.2 s. A small gain, kept because it is free; the larger win came from D20.

## D20 — One combined query per language instead of four
- Alternatives: run defs, refs, imports and entrypoints as separate queries (four tree walks).
- Reason: Profiling `extHostTypes.ts`: parse 24 ms, each query 10–13 ms even with zero matches, because every query walks the whole tree. Concatenating the four files into one query and routing each match by pattern index walks the tree once: extraction 73 → 38 ms on that file, and vscode's cold index 13 s → 8.7 s. Output is identical (golden and property tests unchanged). Tier 2 keeps separate queries because its tags.scm serves as both defs and refs.

## D21 — Reference resolution tiers, with a weighted global fallback
- Alternatives: only same-file/imported/same-package (the plan's list), or any global name match.
- Reason: The plan's three tiers miss most cross-file calls in C (linked via headers, not imports) and re-exports (`from shop import checkout` defined in shop/services.py). A fourth tier accepts a definition anywhere in the same language family only when the name is unique there, with weight 0.5, so it is visibly weaker. Any tier with more than three candidates yields no edge rather than a guess.

## D22 — Python top-level modules resolve only at source roots
- Alternatives: suffix matching anywhere (the first version).
- Reason: Measuring against Python's own PathFinder showed 67 false edges in a 1,000-import sample, e.g. `import datetime` → django/db/models/functions/datetime.py. Python only finds a top-level module in a directory that is not itself a package; enforcing that removed every false edge (1000/1000 agree, 0 extra).

## D23 — Methods declared outside their type are attached to it
- Alternatives: leave Go methods and Rust impl blocks as separate top-level symbols.
- Reason: In Go a method is declared at file level with a receiver; in Rust methods live in `impl` blocks that the first version showed as a second "Order" next to the struct. The extractor now attaches Go methods to their receiver type and merges a Rust impl into the same-named struct/enum/trait in the file (kept separate only when the type lives elsewhere). A type's area is its own lines or its members' lines, whichever is larger.

## D24 — Calls inside Rust macro invocations are not seen
- Alternatives: re-parse macro token trees as expressions.
- Reason: tree-sitter parses macro arguments as token trees, so `println!("{}", order.total())` yields no call edge. Re-parsing token trees is guesswork (macros define their own syntax). Accepted as a known gap; LSP enrichment (M5) adds the semantic edges for visible symbols.
